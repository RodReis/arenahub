# F66 — RLS fase 1 (role de runtime, contexto por transação, primeiras políticas) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** O Postgres passa a recusar, por si só, leitura ou escrita fora do tenant da transação em `students` e `audit_logs` — mesmo que a aplicação esqueça o `where`. RLS é camada 2; `TenantContext` continua obrigatório.

**Architecture:** Um segundo role de banco (`arenahub_app`), sem ownership e sem `BYPASSRLS`, roda a API e os workers. Um `AsyncLocalStorage` carrega o contexto de tenant da requisição; o `PrismaService` intercepta `$transaction` e toda query solta, injetando `set_config('app.tenant_id', ..., true)` **como primeiro comando dentro da própria transação**. Duas políticas RLS (`students`, `audit_logs`) com `FORCE ROW LEVEL SECURITY` leem essa variável via `current_setting()`. Migrations continuam com o role owner.

**Tech Stack:** Prisma 7.9.1, `@prisma/adapter-pg`, PostgreSQL 17, Jest (`.int-spec.ts` em `apps/api`, Vitest em `packages/database`), NestJS.

**Spec:** `docs/specs/SPEC-066-rls-fase-1-role-de-runtime-e-primeiras-politicas.md` · ADR-054

## Evidência experimental que fundamenta o desenho

Rodado em 09/09/2026 contra Postgres 17 real (banco descartável `f66_probe`, role `f66_app` com `NOBYPASSRLS`, tabela `students` com `FORCE ROW LEVEL SECURITY` e política por `current_setting('app.tenant_id', true)`). **O padrão da documentação oficial do Prisma para RLS não serve a este repositório**, e é isso que o plano contorna.

O padrão publicado pelo Prisma envolve cada query num batch `$transaction([set_config, query])`. A doc de shared extensions avisa, em uma linha fácil de perder: *"queries inside this extension will issue on a new connection when invoked inside an existing transaction"*.

| # | Cenário | Resultado observado |
|---|---|---|
| 1 | Extensão abre a própria transação, query solta | Lê só o tenant A |
| 2 | Extensão dentro de `$transaction` interativa já aberta | Roda em **outra conexão** |
| 5 | INSERT dentro de tx externa sem `SET LOCAL` | **Recusado** — `42501`, `new row violates row-level security policy` |
| 7 | `SET LOCAL` na própria `tx`, escreve e lê | Enxerga a própria escrita não commitada |
| 8 | Tenant A lê `students` de B | Zero linhas |
| 9 | Tenant A insere com `tenant_id` de B | **Recusado** — `42501` |
| 10 | Tenant A atualiza linha de B | Zero linhas afetadas |

Conclusões que o plano assume como fato verificado:

1. **O batch `$transaction([set_config, query])` quebra dentro de transação interativa.** O repositório tem mais de 30 `$transaction(async tx => ...)`. Neles o `SET LOCAL` da extensão iria para outra conexão e a escrita seria recusada com `42501` — caso 5.
2. **O desenho correto é `SET LOCAL` na própria `tx`**, como primeiro comando. Casos 7 a 10 provam isolamento completo com atomicidade preservada.
3. **`current_setting(..., true)` devolve `NULL` quando a GUC nunca foi setada**, e a comparação falha em silêncio: leitura devolve zero linhas, escrita estoura `42501`. Zero linhas é indistinguível de "não há dados" — por isso quem **garante** o contexto é o `PrismaService`, não a política. A política é a rede de segurança.

Para reproduzir, o roteiro está no Apêndice A.

## Global Constraints

- RLS é **segunda camada**. Nenhum repositório passa a confiar no banco para filtrar — `TenantContext` continua obrigatório (INV-003). **Nenhuma linha de repositório existente perde o `where: { tenantId }`.**
- Role de runtime `arenahub_app`: **sem ownership**, **sem `BYPASSRLS`**. Migrations correm com o role owner atual.
- `SET LOCAL` / `set_config(..., true)`, nunca `SET` de sessão — o pool do `pg` é compartilhado, e `SET` de sessão vazaria tenant para a próxima requisição que reusar a conexão.
- Operação sem contexto **falha** com erro de domínio, nunca devolve lista vazia.
- Contextos sem request (worker, outbox, edge-sync, seed, elevação) declaram `system` ou `platform` explicitamente. `platform` só no caminho da sessão elevada (ADR-052 §3).
- Escopo: só `students` e `audit_logs`. As doze tabelas restantes são F67.
- Teste de integração roda **sob o role restrito**, não sob o owner — senão o teste mente.
- **Serviço Postgres novo, portas novas** (decisão do PI). Não reaproveitar as portas já configuradas.
- Os 81 pontos de injeção de `PrismaService` e as 461 chamadas **não mudam**. Se uma task quiser tocá-los, a task está errada.

- [ ] **Step 3: Escrever o SQL**

```sql
-- F66 (SPEC-066, ADR-054 §1-4, §6): role de runtime separado do dono das
-- tabelas, e primeiras politicas RLS em students e audit_logs.
--
-- RLS e SEGUNDA CAMADA. TenantContext continua obrigatorio (INV-003) -- esta
-- migration nao dispensa nenhum `where` de repositorio; ela garante que a
-- query que esquecer o `where` nao ve nada, e a escrita errada falha.

-- 1. Role de runtime. NOBYPASSRLS e explicito de proposito: e o ponto
-- central do ADR-054 §2 -- sem ele a politica simplesmente nao se aplica.
-- Senha fica FORA da migration (ver docs/DEVELOPMENT.md).
DO $$
BEGIN
  IF NOT EXISTS (SELECT FROM pg_catalog.pg_roles WHERE rolname = 'arenahub_app') THEN
    CREATE ROLE arenahub_app LOGIN NOBYPASSRLS NOSUPERUSER NOCREATEDB NOCREATEROLE;
  END IF;
END
$$;

-- 2. Dado, nao estrutura: le/escreve nas duas tabelas, mas nao e dono --
-- nao pode DROP, ALTER, nem criar politica.
GRANT USAGE ON SCHEMA public TO arenahub_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON students TO arenahub_app;

-- audit_logs sem UPDATE/DELETE: trilha de auditoria que a aplicacao pode
-- editar nao e trilha de auditoria.
GRANT SELECT, INSERT ON audit_logs TO arenahub_app;

-- 3. FORCE, e nao so ENABLE: sem FORCE o dono da tabela fica ISENTO da
-- politica por padrao, e um script rodando por engano com a URL de migracao
-- vazaria tenant sem avisar.
ALTER TABLE students ENABLE ROW LEVEL SECURITY;
ALTER TABLE students FORCE ROW LEVEL SECURITY;

ALTER TABLE audit_logs ENABLE ROW LEVEL SECURITY;
ALTER TABLE audit_logs FORCE ROW LEVEL SECURITY;

-- 4. Politicas. `current_setting(..., true)` devolve NULL em vez de lancar
-- quando a GUC nunca foi setada; NULL = qualquer coisa e falso, entao a
-- leitura sem contexto ve zero linhas e a escrita sem contexto estoura
-- 42501. Verificado experimentalmente -- ver o plano desta fatia.
--
-- app.actor = 'platform' cobre a sessao elevada de Super Admin (ADR-052 §3),
-- que le entre tenants por desenho, auditada. Nenhuma outra excecao.
CREATE POLICY tenant_isolation_students ON students
  USING (
    tenant_id::text = current_setting('app.tenant_id', true)
    OR current_setting('app.actor', true) = 'platform'
  )
  WITH CHECK (
    tenant_id::text = current_setting('app.tenant_id', true)
    OR current_setting('app.actor', true) = 'platform'
  );

CREATE POLICY tenant_isolation_audit_logs ON audit_logs
  USING (
    tenant_id::text = current_setting('app.tenant_id', true)
    OR current_setting('app.actor', true) = 'platform'
  )
  WITH CHECK (
    tenant_id::text = current_setting('app.tenant_id', true)
    OR current_setting('app.actor', true) = 'platform'
  );

-- Nao ha politica para app.actor = 'system': esse contexto tambem seta
-- app.tenant_id quando opera em nome de um tenant. 'system' descreve QUEM
-- roda, nao um bypass de isolamento.
```

- [ ] **Step 3: Implementar `rls.ts`**

Pontos que o código precisa respeitar, e o porquê de cada um:

- **`set_config($1, $2, true)` com bind, não interpolação.** O terceiro argumento `true` é o que torna o efeito local à transação. Diferente de `SET LOCAL`, `set_config` aceita parâmetro — então não há string montada à mão, e a validação de uuid vira defesa em profundidade, não a única barreira.
- **A validação de uuid fica mesmo assim.** Custa uma regex e fecha a porta caso alguém troque por interpolação depois.
- **`comContexto` é `AsyncLocalStorage.run`.** Nada de variável de módulo: o pool é compartilhado e concorrência embaralharia tenants.
- **`SemContextoDeTenantError` é erro de domínio com código estável**, seguindo o padrão de `erro-de-dominio.ts`. Lista vazia por falta de contexto é o que a Global Constraint proíbe.

## Task 3: `PrismaService` intercepta `$transaction` e query solta

Esta é a task que a evidência experimental redesenhou. **Nenhum repositório muda.**

**Files:**
- Modify: `apps/api/src/persistence/prisma.service.ts`
- Create: `apps/api/src/common/tenant/tenant-rls.middleware.ts` + `.spec.ts`
- Modify: `apps/api/src/app.module.ts`

**Interfaces:**
- Consumes: `contextoRls`, `aplicarContextoNaTransacao`, `SemContextoDeTenantError` (Task 2); `TenantContext` da requisição.
- Produces: nenhuma API pública nova. Os 81 pontos de injeção seguem intactos.

- [ ] **Step 1: Middleware que abre o escopo por requisição**

Roda **depois** do `AuthGuard` ter posto `tenantContext` na requisição. Traduz `TenantContext` para `TenantDbContext`:

- `supportElevation` presente → `{ kind: 'platform' }` (ADR-052 §3);
- caso contrário → `{ kind: 'tenant', tenantId }`.

Rota pública, sem `tenantContext`: **não abre escopo**. Qualquer query que toque tabela protegida ali dentro falha — e é o comportamento certo.

- [ ] **Step 2: Teste do middleware (RED)**

Cobrir os três casos: tenant normal, elevação vira `platform`, ausência de contexto não abre escopo. Jest com `@jest/globals`, no padrão dos `.spec.ts` vizinhos de `apps/api/src/common/`.

- [ ] **Step 3: Interceptar `$transaction` no `PrismaService`**

O núcleo. `$transaction` interativa (callback) ganha o `set_config` como **primeiro comando dentro da própria `tx`**, antes de entregá-la a quem chamou:

```typescript
override $transaction(fn, opcoes) {
  // Forma interativa (callback). A forma em array (batch) cai no super.
  if (typeof fn !== 'function') return super.$transaction(fn, opcoes);

  return super.$transaction(async (tx) => {
    const ctx = contextoRls.getStore();
    if (!ctx) throw new SemContextoDeTenantError();
    await aplicarContextoNaTransacao(tx, ctx);  // set_config dentro DESTA tx
    return fn(tx);
  }, opcoes);
}
```

Três armadilhas, todas verificadas no experimento:

1. **Não abrir transação nova aqui dentro.** É exatamente o que a doc do Prisma faz e o que o caso 5 mostrou falhar: outra conexão, `SET LOCAL` fora do lugar, `42501`.
2. **`$transaction` em array (batch) existe no repo** (`session.repository.ts:65`, `listar-invoices.use-case.ts:78`). Cai no `super` — mas se qualquer item tocar tabela protegida, precisa do mesmo tratamento. Verificar cada uso de array antes de fechar a task.
3. **`this` dentro do callback do `super`.** Chamar um método do próprio serviço ali dentro reentra na intercepção. Usar só a `tx` recebida.

- [ ] **Step 4: Query solta ganha transação própria**

Query fora de `$transaction` (a maioria dos 461 sítios) passa por uma extensão `$allOperations` que a envolve numa transação interativa e aplica o contexto — o mesmo caminho do Step 3, não o batch da doc.

Ponto a resolver na hora: `$extends` devolve um client novo, não muta `this`. Duas saídas, medir e escolher:

- a) aplicar a extensão dentro do próprio `$transaction` interceptado e deixar a query solta ser envolvida por ele;
- b) `PersistenceModule` fornece o client já estendido por `useFactory`, com um provider cuidando de `$connect`/`$disconnect`.

Preferir (a) se resolver, porque não mexe na forma de injeção. **Qualquer que seja, os 81 pontos continuam recebendo `PrismaService` e chamando do mesmo jeito** — se a solução exigir tocá-los, ela está errada.

- [ ] **Step 5: Rodar a suíte unitária inteira da API**

```bash
pnpm --filter api test
```

Mock de `PrismaService` que hoje devolve `$transaction: jest.fn()` pode precisar entregar uma `tx` com `$executeRaw`. Ajustar o mock, nunca o código de produção.

                       tenant_id uuid NOT NULL, name text NOT NULL);
